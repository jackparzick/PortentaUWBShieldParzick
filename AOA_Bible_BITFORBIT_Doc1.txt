## 1) What “full AoA” means in this system
AoA functionality breaks into **four tiers** that map cleanly onto your codebase:

### Tier A — AoA appears in results
You get AoA numbers **inside ranging notifications** and can access them in Arduino code.

- For DS-TWR (two-way), your wrapper struct already has AoA fields.
- For OWR_WITH_AOA (one-way with AoA), your wrapper has types but currently blocks access (union member commented out).

### Tier B — AoA is controllable (configs)
You can explicitly control:
- whether AoA is emitted at all,
- whether azimuth only / elevation only,
- whether AoA fields appear in the report payload,
- whether AoA is bounded/gated by a field-of-view (FoV) concept.

This is split across:
- **Session AppConfig TLVs** (FiRa/UCI “app config”)  
- **Vendor/Extended TLVs** (NXP vendor knobs) with a strict whitelist gate in the `.a`

### Tier C — AoA is “good” (stable and usable)
You add:
- FOM gating
- wrap-safe smoothing
- per-peer state (so one-to-many doesn’t scramble angles)
- a coordinate frame definition + mounting correction

### Tier D — AoA is “advanced” (debug + calibration + multi-session + robustness)
You unlock:
- vendor “extra” payloads: per-antenna-pair AoA/PDoA, FoV flags, SNR/path index
- host-side calibration (always doable)
- optional device-side calibration injection (possible but format-dependent)
- robust stop/start and multi-session coexistence

## 4) AoA configuration model (how AoA output is actually enabled)

**What this means:**
- `AoaResultReq` is an on/off + mode selector (1 byte).

- `0x00`: disable AoA
- `0x01`: enable AoA

#### 4.1.2 ResultReport bitmask semantics
**[LIKELY]** (from your excerpts; verify by behavior):
- bit0: ToF/distance
- bit1: AoA azimuth
- bit2: AoA elevation
- bit3: AoA FOM
So `0x0F` would enable all.

**Practical bring-up rule:**  
Treat `(AoaResultReq=1, ResultReport=0x0F)` as the first attempt. If AoA is still zero, change **one knob at a time**, and log exactly what changes.

## Phase 2 — Make AoA usable (quality gating + smoothing + coordinate frame)
### Objective
Stop treating AoA as a raw sensor. Convert it into a stable signal your application can use.

### 2.1 Define “AoA policy”
Minimum fields:
- `minFomAz`, `minFomEl`
- `rejectIfNlos`
- `boundsEnabled` and bounds:
  - `azMin, azMax`
  - `elMin, elMax`
- `smoothingWindow`
- `mountYawDeg` (start yaw-only)

### 2.2 Implement per-peer state
Key it by:
- `session_handle`
- peer short address (first 2 bytes of peer_addr if using short addresses)

Store:
- rolling window of accepted az/el (and optionally raw + corrected)
- accepted/rejected counters by reason (status vs FOM vs NLOS vs bounds)
- jitter estimate (stddev) for diagnostics

### 2.3 Implement wrap-safe smoothing (critical)
Never average angles directly across ±180.
Do:
- θ → (cosθ, sinθ)
- average vectors
- θ = atan2(avgSin, avgCos)

Do this for azimuth (and optionally elevation if you later treat it as circular).

### 2.4 Coordinate frame definition (prevents “fake bugs”)
Define:
- what “0° azimuth” means on the physical board orientation
- what sign means (left positive vs right positive)

Implement `mountYawDeg`:
- `az_corrected = wrap(az_raw + mountYawDeg)`

Only after yaw is stable do you consider full 3D rotations or IMU fusion.
