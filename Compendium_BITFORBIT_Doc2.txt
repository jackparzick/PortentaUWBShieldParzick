## 2) Arduino wrapper: architecture map (what runs where)

### 2.1 The HAL contract is your “thin waist”
Your wrapper is structured so:
- high-level Arduino code calls methods on a HAL interface (`uwb_hal.hpp`)
- the precompiled `.a` implements those methods (SR150Hardware)

So you can:
- add helper functions in the wrapper freely
- but new deep features (like device config / calibration injection) may require extending the HAL surface unless you call exported `UwbApi_*` symbols directly.

### 2.2 NotificationDispatcher is the single most important chokepoint
Right now:
- It receives raw events and data pointers from the HAL
- It copies a fixed struct size for ranging data (`sizeof(RangingResult)`), wraps it, and calls your callback
- It does **not** preserve variable-length “extra payload”

This affects:
- AoA advanced extras (FoV type 0xA0)
- any other feature relying on variable-length NTF payload

### 2.3 UWBRangingData exposes only part of what exists
- It exposes DS-TWR, TDoA, DL-TDoA accessors
- It does not expose OWR AoA accessor
- It does not expose extra payload bytes

So “full AoA” must include expanding UWBRangingData.

### 2.4 UWBSession init ordering is good for AoA
Your session init order is:
1) sessionInit
2) setRangingParams
3) setAppConfigMultiple
4) setVendorAppConfig

That’s the correct structure for AoA because AoA configs must be applied *before start*.

### 2.5 UWBSessionManager quirk that will bite you later
`addSession()` stores only base session info (session ID/type) and not the derived session instance you created.

This doesn’t block AoA bring-up, but it can confuse multi-session debugging unless you treat SessionManager as “bookkeeping only” or fix it later.

### 2.6 NearbySession/Manager: the phone handshake pipeline
This is the “BLE TLV handshake” path:
- iOS and Android initialize/configure/start/stop via TLVs
- you can later stream AoA back to phone over BLE even if you don’t do “true NI direction” on iPhone

This is an “outside-the-box” but practical system integration path.

## 3) `.a` extraction findings: what is actually possible

### 3.1 Exported AoA-related functions and data (hard proof)
From nm-defined, the `.a` includes:
- `UwbApi_SetAppConfig`, `UwbApi_SetAppConfigMultipleParams`
- `UwbApi_SetVendorAppConfigs`, `UwbApi_GetVendorAppConfigs`
- `UwbApi_SetCalibration`, `UwbApi_GetCalibration`
- `UwbApi_SetDeviceConfig`, `UwbApi_GetDeviceConfig`
- parsing functions: `parseRangingNtf`, `parseTwoWayRangingNtf`, `parseOneWayRangingNtf`
- AoA calibration helpers/tables:
  - `setDefaultAoaCalibration`
  - `aoa_config_block_names`
  - pdoa offsets and thresholds by channel

**Implication:**  
AoA enablement, vendor knobs, and calibration are not missing at the `.a` level.

### 3.2 Vendor TLV gate (the “you cannot brute force this” constraint)
The `.a` has a strict vendor ID whitelist and size-class mapping (see AoA Bible Appendix B).

This means:
- your wrapper enums can list vendor IDs that *exist as names*, but
- the `.a` can still reject them at runtime.

So any “advanced feature” plan must begin by checking:
- is the ID in the whitelist?
- is it 1/2/4/varlen?
- are we sending correct length?

### 3.3 Bus/pins/IRQ are not abstract — they’re hardwired
Disassembly confirms the `.a` uses specific pins for CS/reset/IRQ.

Practical impact:
- if you use those pins for anything else (NeoPixels, random GPIO), you can break ranging notifications and think AoA is dead.

### 3.4 UCIF command engine exists (so “bounded stop” can be engineered)
The zip includes disassembly slices for:
- send command
- retransmit
- timeout

Even if we don’t rewrite UCIF, this tells you:
- there is already retry logic and timeout logic in the stack
- your wrapper must avoid starving the command channel with too much logging / blocking

### 3.5 Role/profile gate strings exist (NI flow constraints)
The zip has “Role not supported” and “Profile ID not supported” callsite mapping info.
This matters for:
- iOS configure flows (profile allowlist / blob sizes)
- Android role gating

Even though this isn’t AoA-specific, it’s part of the “full system correctness” plan.

## 4) The “known gaps” list (everything blocking full functionality today)

### AoA-specific blockers
1) AoA not enabled in examples by default
2) No AoA convenience setters in `UWBAppParamList`
3) Vendor AoA knobs not surfaced by typed helpers (must build TLVs manually)
4) OWR AoA blocked by:
   - union member commented out
   - missing accessor
5) Advanced AoA vendor extras blocked by:
   - NotificationDispatcher dropping extra bytes
   - UWBRangingData not owning extra payload

### Robustness/system blockers (will matter later)
1) SessionManager stores only base session info
2) Nearby stop loop may be slow/unbounded (needs tightening in production)
3) No easy “GetAppConfig readback” path exposed at Arduino level (slows debugging)

This is the “don’t build castles on sand” checklist:

### AoA bring-up verification

  - AoaResultReq (0x0D) + ResultReport (0x2E)

- varlen blobs:
  - discover expected length/format via controlled experiments

- confirm extra_length becomes nonzero
- confirm extra bytes are contiguous in callback memory (if not, plan changes)

### OWR verification
- confirm measureType==OWR_WITH_AOA can be observed at all on your firmware/profiles
- confirm expected count=1 unless proven otherwise

### Stress verification
- 100 start/stop cycles without hang
- peer drop mid-session does not hang stop/teardown

### A2) Units & scaling section (don’t leave it implicit)
AoA fields are `int16_t`. That does **not** automatically mean “degrees” — you need to determine scaling.

#### A2.1 Angle units hypotheses (ranked)
- **Hypothesis H1 (centi-degrees):** raw = degrees × 100  
  - Example: 4500 means 45.00°
- **Hypothesis H2 (Q format):** raw is fixed-point, e.g. Q9.7 or Q8.8  
  - Your wrapper defines multiple Q conversion macros, so fixed-point is plausible.
- **Hypothesis H3 (degrees directly):** raw = degrees (rare if int16 is used to carry fractional degrees)

#### A2.2 FOM meaning hypotheses
- **Hypothesis F1:** 0–255 quality score (most likely for uint8)  
- **Hypothesis F2:** 0–100 (scaled)  
Either way: you will threshold it empirically, not by guess.

#### A2.3 10-minute scaling experiment (fast truth serum)
Setup:
- Put controller fixed on table, define a “forward” axis.
- Keep tag at fixed distance (2–4m), LOS.
- Rotate the **controller** in known increments while keeping tag stationary (or rotate tag around controller).
Record:
- raw `aoa_azimuth` and `aoa_azimuth_fom` for ~200 samples per pose.

Poses:
- 0°, +45°, +90°, -45°, -90° (at least these).

Analysis:
- Compute mean raw value per pose.
- Fit linear model: `raw ≈ scale * deg + offset`
- If the fit is very linear and scale is around:
  - ~100 → centi-deg
  - ~128/256-ish → Q format
- Determine sign convention: which direction corresponds to positive.

Lock down:
- One conversion function (raw → degrees)
- One sign convention statement
- One mounting yaw offset default

### A5) Validity gating spec for AoA samples
Formalize what counts as “usable.”

#### Reject conditions (initial spec)
Reject if any of:
- `status != 0`
- `distance == 0xFFFF`
- `fomAz < minFomAz`
- `fomEl < minFomEl` (only if you use elevation)
- `nlos == 1` (optional gate; treat as “reject by default” for stable UI)
- `az` outside bounds if bounds enabled
- `el` outside bounds if bounds enabled

#### Accept conditions
Accept if:
- all required fields present and pass thresholds
- and sample passes wrap-safe smoothing pipeline

#### Reason codes (loggable)
- `R_STATUS`
- `R_DIST_INVALID`
- `R_FOM_AZ`
- `R_FOM_EL`
- `R_NLOS`
- `R_OOB_AZ`
- `R_OOB_EL`

#### Default starting thresholds (placeholders)
- `minFomAz = 60` (tune)
- `minFomEl = 60` (tune)
- bounds: az ±90°, el ±60° (tune)
- smoothing window: 5–9

### A6) Raw notification capture / replay plan
This becomes essential once you touch:
- varlen vendor blobs (0x85/0x74/0x03)
- extra payload parsing (0xA0)

#### Capture
- Add a toggle to log:
  - `measureType`, `no_of_measurements`, `extra_data_type`, `extra_length`
  - raw bytes of extra payload (first N bytes)
- Write log lines in a machine-parsable format (e.g., hex string with metadata header).

#### Replay harness
- A tiny offline script (Python or C++) that:
  - reads captured hex payload
  - re-runs parsing functions (your own parser) on it
  - prints decoded AoA/PDoA and sanity checks lengths/offsets

This lets you iterate parsing without reflashing hardware.

### A7) Payload-size & memory safety constraints
When you start preserving `extra_length`, you must define hard rules.

#### Max extra length
- Choose a safe cap (e.g., 512 or 1024) initially.
- Add counters:
  - `extra_truncated_count`
  - `extra_oversize_last_len`

#### Oversize behavior
- truncate to max
- log a warning **rate-limited** (once per second)
- keep running (don’t crash)

#### Allocation policy
Prefer:
- fixed ring buffer or fixed per-event static buffer (if feasible)
Over:
- per-event malloc/free (can fragment and crash over time)

## Additions to Document 2 (Compendium)

### B1) Glossary + naming map
#### Glossary
- **UCI**: UWB Command Interface (command/notification protocol)
- **UCIF**: UCI interface layer (send/retry/timeout engine)
- **TML**: transport middleware layer (SPI/IRQ transport)
- **NTF**: notification (asynchronous message)
- **TLV**: type-length-value
- **STS**: scrambled timestamp sequence (security)
- **FOM**: figure of merit (quality/confidence)
- **PDoA**: phase difference of arrival (raw phase-based measurement)
- **AoA**: angle of arrival (azimuth/elevation derived from PDoA/antenna geometry)

#### Naming map (wrapper vs `.a` vs logs)
- Wrapper: `AppConfigId::AoaResultReq` ↔ `.a` strings: `UCI_PARAM_ID_AOA_RESULT_REQ`
- Wrapper: `VendorAppConfigId::AZIMUTH_FIELD_OF_VIEW` ↔ `.a` gate: varlen ID 0x85
- Wrapper: `twr_mesr.aoa_azimuth` ↔ `.a` strings: `aoa_azimuth_FOM` etc.
- Wrapper: `extra_data_type/extra_length` ↔ `.a` strings: `FOV_SPECIFIC_DATA_TYPE 0xA0`

### B2) Symptom → probable layer cheat sheet
| Symptom | Most likely layer | First checks |
